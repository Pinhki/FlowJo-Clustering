# Generated FlowJo-biexponential prompt evaluation — 2026-08-26

- The prompt correctly requires event-level transformation before per-cluster medians, retaining compensated negative values, separating signal transformation from clustering/display scaling, and avoiding a homemade approximation.
- Much of the requested infrastructure already exists: WSP import extracts per-channel transforms with `gh_get_transformations()`, stores them on each registry entry, and `axis_scale_helpers.R` evaluates exact `flowWorkspace::flowjo_biexp()` forward/inverse transforms. `flowWorkspace` is already an app dependency.
- The Cluster compute/heatmap path is separate and still uses `flowCore` Logicle (`estimateLogicle()` or `logicleTransform()`). The heatmap correctly transforms events before computing cluster medians, but it does not yet reuse the exact WSP per-channel settings.
- The prompt's generic `channelRange=4096`, `maxValue=262144`, etc. must not override imported WSP parameters. The current reference WSP includes materially different per-channel values, commonly `channelRange=256`, `maxValue=4194304`, and varying `widthBasis`/`pos`.
- Calling `channelRange=1024` a "FlowSOM-like scale" is misleading: the app explicitly disables scaling inside FlowSOM, and FlowSOM does not define that normalization. It is a FlowJo transform display-coordinate choice. It is also not a hard 0–1024 normalization: with the proposed defaults, values outside the transform's nominal domain can produce coordinates below 0 or above 1024.
- In the current heatmap matrix, rows are clusters and columns are markers. Therefore "within each marker across clusters" is the existing **column** z-score/min-max option, not row scaling. The prompt's requested label/formula conflicts with the app's matrix orientation.
- Current heatmap choices already include none, row z/min-max, and column z/min-max; only the default differs (`row_z` currently). “None / raw” is mislabeled because it shows transformed per-cluster medians, not raw fluorescence.
- A safe implementation should reuse/generalize the existing exact FlowJo transform helper, preserve WSP-specific settings when available, provide a clearly labeled generic fallback only when needed, avoid associating 1024 with FlowSOM, and decide explicitly whether changing the heatmap default should affect old saved runs/UI expectations.
